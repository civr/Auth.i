# Keystone — Design Spec

Date: 2026-10-04
Status: Draft for review

## 1. Purpose

Keystone is a small, self-hosted identity provider (in the spirit of authentik) for one owner's
homelab/VPS. It gives the owner's own apps single sign-on and keeps their user/group lists in sync.

Success criteria:

- A new app can be connected in under 5 minutes (OIDC or forward-auth), using copy-paste snippets
  generated by Keystone.
- Users can sign in with: local account, on-prem AD (LDAPS), Entra ID / Office 365 (SAML or OIDC).
- Users and groups are pushed to apps via SCIM 2.0.
- Everything the admin UI can do is also available through a REST API.
- Runs with `docker compose up` (Keystone + Postgres) behind an existing reverse proxy with TLS.

Non-goals (v1): WebAuthn/passkeys, Keystone as SAML IdP towards apps, multi-tenancy, LDAP server
outpost, horizontal scaling beyond one instance, thousands of users.

## 2. Architecture

```
            ┌──────────────── upstream sources ────────────────┐
            │  Local DB   AD (LDAPS)   Entra (SAML)   Entra (OIDC) │
            └─────────────────────────┬────────────────────────┘
                                      │ authenticate + JIT/sync
                       ┌──────────────▼──────────────┐
  browser ───────────▶ │           Keystone            │ ──▶ Postgres
                       │ Fastify + oidc-provider     │
                       └──┬────────────┬──────────┬──┘
          OIDC/OAuth2     │ forward-   │  SCIM 2.0│ push
                          ▼ auth       ▼          ▼
                      App A (OIDC)  Reverse proxy  App C (SCIM endpoint)
                                    → App B
```

- Runtime: Node.js 24 LTS, TypeScript (ESM), Fastify.
- Containers: `keystone` and `postgres:17`. No Redis.
- Single process. Background jobs (SCIM outbox worker, LDAP sync, cleanup) run in-process on timers,
  using Postgres row locks (`FOR UPDATE SKIP LOCKED`) so a second instance would not double-process.

### Key libraries

| Concern | Library |
|---|---|
| OIDC/OAuth2 provider | `oidc-provider` (panva, OpenID certified) |
| Upstream OIDC (Entra) | `openid-client` |
| SAML SP (Entra) | `@node-saml/node-saml` |
| LDAPS | `ldapts` |
| Passwords | `argon2` (argon2id) |
| TOTP | `otpauth` |

| Templates (admin/login UI) | `eta` server-rendered, `htmx` for small interactions |
| Tests | `vitest` |

## 3. Modules

Source layout: `src/<module>/`. Each module exposes a small service interface; HTTP routes live in
`src/http/` and call services only.

### 3.1 identity
Owns users, groups, memberships and external identity links.

- `users`: id (uuid), username (unique), email (unique, nullable), display_name, given_name,
  family_name, is_active, is_admin, password_hash (nullable), totp_secret_enc (nullable),
  created_at, updated_at.
- `groups`: id, name (unique), description, source_id (nullable: null = local group),
  external_id (nullable).
- `group_members`: group_id, user_id.
- `identities`: id, user_id, source_id, external_id (immutable upstream id: AD `objectGUID`,
  Entra `oid`, SAML NameID), last_login_at, raw_attributes (jsonb).

Linking rule on upstream login:
1. Find `identities` by (source_id, external_id) → that user.
2. Else, if the source has `link_by_email = true` and a user with the same verified email exists →
   link to that user.
3. Else, if the source has `jit_provisioning = true` → create user + identity.
4. Else → reject login with a clear message.

Groups from a source are mirrored as groups with `source_id` set; membership of source-owned groups
is replaced on each login/sync. Local groups are never touched by sources.

Every mutation of users/groups/memberships emits a domain event (see 3.7).

### 3.2 sources
Table `sources`: id, slug (unique, used in URLs), type (`local|ldap|saml|oidc`), name, enabled,
config (jsonb, secrets encrypted), jit_provisioning, link_by_email, sort_order.

- **local**: username/email + argon2id password. Optional TOTP per user (enforced if enrolled).
  Exactly one local source exists and cannot be deleted.
- **ldap** (on-prem AD): config `url` (ldaps://), `bind_dn`, `bind_password`, `base_dn`,
  `user_filter` (default `(&(objectClass=user)(|(sAMAccountName={u})(userPrincipalName={u})))`),
  `group_base_dn`, attribute map, `ca_cert` (PEM, optional), `tls_verify` (default true),
  `sync_interval_minutes` (0 = off).
  Login: service bind → search user → bind as user DN with given password → read attributes and
  `memberOf` → link/JIT. `{u}` is LDAP-filter-escaped.
  Sync: periodic search of users in base_dn; updates attributes, group memberships; users not found
  or disabled (`userAccountControl` bit 2) are set inactive (never deleted).
- **saml** (Entra ID): Keystone is SP. Config: `idp_entity_id`, `idp_sso_url`, `idp_cert`
  (or `idp_metadata_url`, fetched and cached), `sp_entity_id` (default `<issuer>/source/saml/<slug>`),
  attribute map (defaults for Entra claim URIs incl. `.../claims/groups` and
  `.../identity/claims/objectidentifier`). Endpoints: `GET /source/saml/<slug>/metadata`,
  `GET /source/saml/<slug>/login`, `POST /source/saml/<slug>/acs`. Signed assertions required;
  InResponseTo validated against a short-lived request store.
- **oidc** (Entra ID or any OIDC IdP): config `issuer`, `client_id`, `client_secret`, `scopes`,
  claim map (Entra `oid` as external_id, `groups` claim). Auth code + PKCE + state + nonce.
  Endpoints: `GET /source/oidc/<slug>/login`, `GET /source/oidc/<slug>/callback`.

Note on Entra groups: Entra emits group object IDs by default. The group mapping table
`source_group_map` (source_id, external_id, display_name) lets the admin give them names; unmapped
IDs become groups named by their ID.

### 3.3 provider (OIDC to apps)
- `oidc-provider` mounted at `/oidc`. Issuer = `KEYSTONE_ISSUER_URL` + `/oidc` (e.g. `https://auth.example.com/oidc`).
- Flows: authorization code + PKCE, refresh token, client credentials. No implicit.
- Scopes/claims: `openid`, `profile` (name, given_name, family_name, preferred_username),
  `email` (email, email_verified), `groups` (array of group names).
- Clients stored in table `applications` (see 3.5) and served through a custom adapter;
  provider's own artifacts (sessions, grants, codes, tokens) in table `oidc_payloads`
  (id, type, payload jsonb, grant_id, uid, expires_at) with periodic cleanup.
- Signing keys: RS256 + ES256 JWKS stored encrypted in `signing_keys`; rotation via API keeps the
  previous key published until its tokens expire.
- Login/consent interactions handled by Keystone's own login UI; consent auto-granted for
  first-party apps (all apps are first-party here) — configurable per app.

### 3.4 forward-auth
For apps without login code, behind Traefik / Caddy / nginx.

- `GET /outpost/auth` — proxy calls this with original request headers
  (`X-Forwarded-Host/Uri/Proto/Method`).
  - Valid Keystone session cookie and user allowed for the matched application → `200` with headers
    `X-Keystone-User`, `X-Keystone-Email`, `X-Keystone-Name`, `X-Keystone-Groups` (comma-separated),
    `X-Keystone-Uid`.
  - No session → `302` to `/login?rd=<original url>` (Traefik/Caddy) or `401` when
    `?mode=nginx` (nginx `auth_request` then redirects via `error_page`).
  - Session but not allowed → `403`.
- Session cookie `keystone_session` set on `KEYSTONE_COOKIE_DOMAIN` (e.g. `.example.com`), HttpOnly,
  Secure, SameSite=Lax. Server-side sessions in table `sessions`.
- Redirect targets validated: host must match a registered forward-auth application or be under
  the cookie domain (no open redirect).
- Application matching by host (`external_host` of application).

### 3.5 applications & policy
Table `applications`: id, slug, name, type flags (`oidc_enabled`, `forward_auth_enabled`),
`client_id`, `client_secret_enc`, `redirect_uris[]`, `post_logout_redirect_uris[]`,
`external_host` (forward-auth), `allowed_group_ids[]` (empty = all active users),
`skip_consent` (default true), `launch_url`, created_at.

Policy check `canAccess(user, app)`: user active AND (allowed groups empty OR user in any allowed
group). Enforced at OIDC authorization, token refresh, and forward-auth.

User dashboard at `/` lists apps the user can access (launch_url).

### 3.6 scim (push provisioning)
Table `scim_targets`: id, application_id, base_url, token_enc, enabled, scope
(`all_users` | `app_users` = users passing app policy), last_full_sync_at, status.
Table `scim_resources`: target_id, local_type (user|group), local_id, remote_id, last_hash.
Table `scim_outbox`: id, target_id, op, local_type, local_id, attempts, next_attempt_at,
last_error, created_at.

- Domain events (user created/updated/deactivated, group created/updated/deleted, membership
  changed) enqueue outbox rows for each enabled target whose scope covers the user.
- Worker processes outbox: SCIM 2.0 (RFC 7643/7644) `POST /Users`, `PUT /Users/{id}`,
  `PATCH active=false` for deactivation (never DELETE users), `POST/PUT/PATCH /Groups`
  with `members`. Bearer token auth.
- Retry with exponential backoff (1m → 6h cap, max 20 attempts), then status `failed`, visible in UI.
- Full reconcile: nightly + on demand. Looks up existing remote resources by `userName` /
  `displayName` filter, adopts them, then creates/updates missing ones. Users removed from scope
  are deactivated on the target.
- User mapping: `userName`=username, `externalId`=Keystone user id, `name.givenName/familyName`,
  `displayName`, `emails[primary]`, `active`.

### 3.7 events & audit
- In-process event bus (typed), used by scim and audit.
- `audit_log`: id, at, actor (user id | api token id | system), action, target, details jsonb, ip.
  Logged: logins (success/fail), admin changes, token creation, SCIM failures.

### 3.8 admin API & UI
- REST under `/api/v1`, JSON, zod-validated. Auth: `Authorization: Bearer <api token>`
  (table `api_tokens`: id, name, token_hash sha256, created_by, last_used_at, expires_at)
  or admin session cookie + CSRF token.
- Resources: `users`, `groups`, `groups/{id}/members`, `sources`, `sources/{id}/sync`,
  `sources/{id}/test`, `applications`, `applications/{id}/secret` (rotate),
  `applications/{id}/snippets`, `scim-targets`, `scim-targets/{id}/sync`, `scim-targets/{id}/outbox`,
  `api-tokens`, `audit-log`, `keys/rotate`.
- OpenAPI document served at `/api/v1/openapi.json`.
- Admin UI at `/admin`, server-rendered with eta + htmx, uses the same service layer.
  Pages: dashboard, users, groups, sources (with "test connection"), applications (with
  connection snippets), SCIM targets (status/outbox), API tokens, audit log.
- Snippets generated per app: Auth.js/NextAuth provider config, Express (`openid-client`),
  Python (Authlib), Traefik labels, Caddy `forward_auth`, nginx `auth_request`, `.env` block.

### 3.9 login UI
- `/login`: local form + buttons per enabled upstream source; LDAP sources share the
  username/password form (tried in `sort_order`: local first, then LDAP sources).
- `/login/totp` second step when enrolled. `/logout` (also OIDC RP-initiated logout).
- `/me`: profile, change local password, enroll/disable TOTP.

## 4. Configuration

Environment (everything else lives in the DB and is managed via API/UI):

| Var | Purpose |
|---|---|
| `KEYSTONE_ISSUER_URL` | public base URL, e.g. `https://auth.example.com` |
| `KEYSTONE_COOKIE_DOMAIN` | e.g. `.example.com` |
| `KEYSTONE_SECRET_KEY` | 32-byte base64; encrypts secrets at rest, signs cookies |
| `DATABASE_URL` | Postgres URL |
| `KEYSTONE_BOOTSTRAP_ADMIN_USER` / `_PASSWORD` / `_EMAIL` | creates first admin if no users exist |
| `KEYSTONE_TRUST_PROXY` | trusted proxy CIDRs for `X-Forwarded-*` |
| `LOG_LEVEL` | pino log level |

## 5. Security

- Secrets at rest: AES-256-GCM with key derived from `KEYSTONE_SECRET_KEY` (HKDF, per-purpose).
- Passwords: argon2id. API tokens and session ids: 32 random bytes, stored as SHA-256 hash.
- CSRF tokens on all cookie-authenticated state-changing requests.
- Login rate limiting per IP and per username (in Postgres, sliding window).
- LDAP filter escaping; LDAPS certificate verification on by default.
- SAML: signature required, audience + destination + InResponseTo + time checks (node-saml).
- Strict redirect validation for `rd` parameters and OIDC redirect URIs (exact match).
- Security headers (CSP, frame-ancestors none, HSTS when https).
- Audit log for auth and admin events.

## 6. Error handling

- Upstream source unreachable → login page shows source-specific error; other sources unaffected;
  logged + audited.
- LDAP sync errors abort that sync run without deactivating anyone (no mass deactivation on outage).
- SCIM errors → retry with backoff; 4xx (except 429/409) marked failed immediately with response
  body stored; 409 on create triggers adopt-by-filter.
- API returns RFC 7807 problem+json.

## 7. Testing

- vitest unit tests per module (identity linking, policy, crypto, snippets, SCIM mapping/diff,
  redirect validation, LDAP filter escaping).
- Integration tests using Docker services from `docker-compose.test.yml`: Postgres, OpenLDAP with
  TLS (`osixia/openldap` or `bitnami/openldap`), a small mock SCIM server (in-repo, Fastify).
- E2E OIDC: spin up Keystone in-process, drive auth code + PKCE with `openid-client` as RP.
- SAML: in-test IdP using a generated key pair to sign responses (node-saml / xml-crypto).
- Upstream OIDC: in-test mock IdP (`oidc-provider` instance acting as Entra).
- Entra ID real tenant: manual checklist in `docs/entra-setup.md`.
